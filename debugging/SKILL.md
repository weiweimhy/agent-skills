# 故障定位

## 适用范围

用户要求解释或修复已有的错误、崩溃、构建失败、性能退化、服务不可用或结果偏差时使用。若任务只要求审查潜在问题，使用代码审查流程；若目标是比较候选方案或验证新假设而没有既有故障，使用实验设计流程。

## 调查步骤

1. 从仓库的 `AGENTS.md`、项目文档和现有配置确认项目边界、运行方式与本地约定。识别实际宿主、操作系统、Shell、语言版本和相关依赖；
   不要把某个编辑器、终端或 CI 的行为假设为所有环境通用。
2. 明确预期、实际结果、触发条件、影响范围和最近变化。保留原始错误、退出码、时间点和环境信息；区分用户观察到的事实与尚未验证的猜测。
3. 尝试复现。优先缩小到最小输入和最短路径；记录准确命令、工作目录、关键配置及必要前置条件。复现不了时，列出还缺少的证据，不得把猜测写成根因。
4. 沿数据和控制流从触发输入追踪到出错边界，再回到相关调用方。提出少量可证伪的根因假设，先用成本低、风险小且能区分假设的检查验证；检查已有日志、代码、配置和版本事实，不以反复重试代替分析。
5. 用户要求修复时，针对有证据支持的根因做最小改动，并检查相邻失败路径、状态边界和兼容性。涉及删除数据、变更共享环境、重启服务、外部网络调用或部署时，先确认当前任务是否已授权该副作用；只读调查不扩大为外部变更授权。
6. 依据仓库现有说明选择实际可用的验证命令。报告确实执行过的命令和结果；区分真实程序运行、静态检查、模拟环境与测试夹具。没有运行的检查不得表述为通过。

## 跨宿主约定

- 先读取当前环境提供的项目说明、脚本入口和工具版本，再选择命令；不臆造工具、脚本、路径或服务状态。
- 在不同 Shell 或操作系统间迁移步骤时，明确工作目录、路径和引号语义；有差异时给出与当前环境匹配的命令，不把某个 Shell 的语法伪装成通用语法。
- 对可能变化的配置、依赖和运行环境，用当前仓库或可访问的权威证据核实。时间敏感的事实不能只凭记忆。
- 减少输出中的敏感信息。日志可能含凭据、个人数据或内部标识；引用时仅保留定位问题所需片段，并避免复制到不受控文件或外部服务。

## 交付

简要说明：观察到的症状和复现条件、被证据支持的根因及信心、做过的改动、实际运行的验证和结果，以及仍未确认的部分。若仍有多种合理解释，明确说出各自所缺的证据和下一项最有区分力的检查。
