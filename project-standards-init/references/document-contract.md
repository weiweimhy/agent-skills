# 项目文档契约

## 选择原则

文档范围由仓库事实与用户授权决定。依赖清单、源代码、配置、运行脚本、CI、现有文档和已确认的运行方式均可作为证据；目录名、计划采用的技术和知识库中存在的笔记都不是已实现的证据。
获授权建立前端基线时，可记录本次设计决策与实施计划；必须与已有事实分开，不将计划写成已安装、已实现或已验证。
下列条件决定授权范围内哪些文档有价值，不扩大用户指定的文件范围。
例如“仅刷新 AGENTS.md”时，不自动新增 UI 交付文档，即使项目已有可记录范式。

## 初始化诊断与修复建议

每次初始化或刷新完成后，都在交付汇总中给出“初始化后修复建议”。这不是新的项目文档，除非用户另有要求；它应让维护者能据此安排后续修复。

| 分类 | 判定条件 | 建议应包含的内容 |
| --- | --- | --- |
| 缺失 | 已确认的项目事实需要某项规则、文档、范式或验证能力，而项目没有相应覆盖 | 目标、事实证据、影响、优先级和最小补齐步骤 |
| 过时或冲突 | 现有文档或规则与代码、配置、真实命令结果或用户已确认决定矛盾 | 冲突的文件和内容、相反的事实、影响与更新建议 |
| 未验证 | 项目声明或文档要求某项命令、流程或验收，但本次不能证明其可执行 | 未验证范围、原因、风险与可执行的验证步骤 |
| 需要决策 | 可靠交付依赖产品、设计、架构或验收选择，而仓库事实无法确定 | 所需决定、已知选项或约束、影响和应由谁确认 |

每项建议使用统一字段：优先级（阻止开发、下一项功能前、可延后）、类别、目标、证据、影响和最小下一步。缺少可选最佳实践、未采用工具或可优化措辞不构成“缺失”或“过时”；它们最多作为可延后的建议，且必须明确是建议而非问题。

## 基础交付物

### `AGENTS.md`

根目录 `AGENTS.md` 说明项目目标、实际技术栈、目录职责、架构边界、依赖规则、编码与测试要求、
真实可运行的常用命令、变更流程和禁止事项。它保持简洁，并要求代理在修改前检查同类实现、
契约与测试，在修改后报告真实执行的验证。对超出授权的新流程、公开契约、持久化数据或整体设计替换等高影响
选择，要求先给出方案并等待确认；授权内的可逆设计细节直接决定。详细设计、测试和交互规则链接至 `docs/`。
有前端规范时，加入前端设计契约中的简短后续开发规则，链接实际的视觉规范与交付文档，避免初始化后风格漂移。

### `docs/architecture.md`

在项目包含多个职责模块、外部系统或重要数据流时创建。描述系统边界、模块职责、依赖方向、关键数据流和真实的 Mermaid 架构图。简单单文件工具可不创建，或明确标注为“待随项目扩展补充”。

### `docs/development.md`

在仓库有可运行的开发、构建或验证流程时创建。记录环境要求、安装、配置、启动、构建、测试、格式化和排错，并且每条命令须来自实际仓库。不能确认的内容写为“待补充”。

### `docs/testing-and-quality.md`

在项目存在业务逻辑、自动化测试、构建步骤或发布风险时创建。定义当前项目实际可执行的测试层级、质量门槛和关键风险场景；不虚构覆盖率阈值或 CI 工作流。

### `docs/ui-design.md` 或已有设计文档

在前端初始化的沿用与提炼或建立基线模式下维护；只有框架依赖、且用户只要求事实审计时不生成。
已有 `DESIGN.md` 或等价视觉规范时直接维护并链接它，不建立第二套权威来源。
按 [前端设计契约](frontend-design-contract.md) 记录具体风格、语义 token、布局、
组件变体与状态、图标系统、动效与减少动态效果策略，以及代表页面和后续开发规则。
为规则注明已有事实、本次设计决策、待实现或待验证；真实与计划中的代码路径分开。

设计方向应适合产品和页面任务，不能将外部技能偏好的字体、颜色、组件库或动效库当成所有项目的默认。
规范与 token 实现之间标注映射；共用一个数值来源，交付文档引用视觉规范而不复制整套规则。

### `docs/ui-delivery.md`

以下任一路径成立时维护：

- 已存在 Web、桌面或游戏 UI，且有独立于运行时的交付事实：已批准的产品或设计来源、
  可复用且有交互边界的范式，或真实视觉/设备验收方式。
- 用户授权建立前端基线，且本次已形成具体设计契约。此时可记录未来验收计划，
  明确当前尚未实现的 UI、依赖、示范页面与待验证项。

记录设计规范入口、组件与主题实现位置、代表页面、数据/本地/URL 状态边界、国际化、
加载、空、失败、权限、提交中和危险操作要求；说明键盘、焦点、响应式和目标设备限制。
图标和动效参数引用视觉规范，在此记录如何实际检查一致性、快速重复操作和减少动态效果模式。
自动化命令必须来自仓库；无自动化能力时提供可复现的人工操作与预期结果，标明尚未执行。

分别标明产品与设计事实、已安装运行时、可选 Skill/MCP/浏览器工具和外部参考。
组件库能力不等于设计来源，工具存在不等于已采用截图回归；截图存在也不证明动画已验收。
纯审计项目若只有 UI 运行时事实而没有交付事实，不创建空模板，在汇总中记录缺口。

## 按技术栈选择的规范文档

在 `docs/standards/` 中只创建下列经证实需要的文件。
新项目用户已明确选定的技术也可形成规范，但标为“已选定／尚未安装实现”；
实际采用情况与命令留待脚手架建立后核实，不把候选技术当作已选定方案。

| 已确认的项目事实 | 生成的规范文档 | 关注点 |
| --- | --- | --- |
| Go 业务代码或服务 | `go.md` | 包边界、context、错误、并发、测试 |
| Vue 与 TypeScript | `vue-typescript.md` | 页面、组件、组合式函数、状态、类型 |
| React 与 TypeScript | `react-typescript.md` | 页面/模块、组件、Hooks、状态、异步、类型、无障碍、测试 |
| Node.js 工具链 | `nodejs.md` | 包管理、脚本、环境变量、构建 |
| Tailwind 或已证实的同类原子化样式方案 | `tailwind-ui.md` | 令牌、组件复用、响应式、状态展示；不适用于其它 UI 运行时 |
| 前端规范提炼或获授权建立基线 | `docs/ui-design.md` 或已有设计文档 | 风格、token、组件、图标、动效的唯一规范来源 |
| UI 交付事实或本次前端契约 | `docs/ui-delivery.md` | 实现状态与验收计划 |
| Unity 与 C# | `unity-csharp.md` | 生命周期、资源、事件、对象池、性能 |
| Lua 游戏逻辑 | `lua.md` | 模块、数据、错误、性能、调试 |
| C# 与 Lua 绑定 | `unity-csharp-lua.md` | 语言职责、DTO、热更、高频调用 |
| Go 与 Wails 桌面集成 | `wails.md` | 绑定层、系统能力、权限、打包 |
| Python 工具或服务 | `python.md` | 环境、CLI、类型、日志、可重复执行 |

## 条件交付物

- 当存在 HTTP、RPC、消息通信或本地持久化时，创建 `docs/api-and-data.md`，说明真实接口契约、鉴权、错误、时间、ID、幂等和迁移边界。
- 仅在仓库或用户已明确记录了重要技术取舍时，创建 `docs/decisions/` 下的 ADR；ADR 记录事实、上下文、决定和后果，不补写历史猜测。
- 仅当仓库实际部署到 Nginx、使用 Redis 或具有对应代码与配置时，在适当规范文件中纳入这些约束；没有证据就不建立专属文档。

## 常见技术栈组合

- Go API 服务通常需要 Go、接口与数据、质量规范；Nginx 与 Redis 仅在已确认时加入。
- Vue Web 项目通常需要 Vue/TypeScript、Node.js、质量规范；Tailwind、已确认的 UI 运行时和接口数据分别按依赖、源码、配置或已确认项目事实决定。
- React Web 项目通常需要 React/TypeScript、Node.js 和质量规范。Tailwind、已确认的 UI 运行时、接口与数据文档仅在仓库依赖、代码、配置或已确认项目事实证明需要时加入。
- 已有 UI 的项目提炼视觉规范；获授权初始化前端且产品目标明确时建立设计基线。
  按上述条件维护 `docs/ui-delivery.md`；实际框架和测试工具的规范仍须有采用证据。
  纯审计缺输入时只记录缺口；Skill、MCP、外部网站或截图目录不构成采用证据。
- React 项目不默认生成 Vue、Tailwind、Next.js、Redux、Zustand、React Router
  或 TanStack Query 的专属规则；每项均需由仓库事实证实。
- Unity 项目需要 Unity/C#；Lua 及协作边界仅在 Lua 运行时和绑定关系存在时加入。
- Go + Wails 桌面项目需要 Go 与 Wails；Vue、Tailwind 和 Node.js 规范只在前端实际使用时加入。
- Python 工具通常需要 Python、通用架构和质量规范；API 与数据文档以外部通信或存储为条件。

## 完成检查

- 文档中的目录、命令、依赖、模块和数据流均可在仓库或用户确认的信息中追溯。
- 每一项技术规范都对应真实采用的技术；没有空文档、无关文档或重复说明。
- `AGENTS.md`、架构、开发说明、测试策略和用户可见配置说明保持一致。
- 对已确认存在 UI 且生成该文档的项目，`docs/ui-delivery.md` 与现有组件、主题、页面范式
  和实际视觉验收方式一致，并区分项目设计事实、已确认运行时、可选开发工具和经批准的外部参考。
- 新建前端的视觉规范有具体 token、组件状态、图标和动效决定，且与后续开发规则相连；
  不把尚未实现的设计或验收计划描述为已有能力。
- 对无 UI 且没有前端初始化授权的项目，以及纯审计缺少交付事实的项目，不生成空 UI 文档。
- 修改的 Markdown 已通过可用 lint 检查，或已报告工具缺失与人工检查范围。
