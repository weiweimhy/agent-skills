# 项目规范初始化

为当前仓库建立与真实技术栈一致、可执行且可维护的协作规范和工程文档。将通用知识库作为经验来源，而不是项目事实来源。

## 适用范围

- 用户要求初始化新项目、补齐或重建 `AGENTS.md`、架构文档、开发文档或项目技术规范。
- 仓库已经存在，或用户已提供足以确认技术栈、项目目标和输出位置的项目说明。

不用于日常功能修改、单篇文档润色，或尚未提供仓库与项目事实的纯技术选型讨论。
用户限定只更新某个文件（例如仅 `AGENTS.md`）时，交付物条件不扩大授权范围；
其它文档仅在汇总中建议，不自动创建。

## 前端初始化分支

按 [前端分支与文档判定](references/document-contract.md#前端分支与文档判定)
确定模式和交付物；该表是分支与文档生成条件的唯一来源。
进入 UI 范围后，读取 [前端设计契约](references/frontend-design-contract.md)，
按选定范围提炼或建立视觉、组件、图标与动效规则，并将实际设计入口链接到 `AGENTS.md`。
初始化只制定与连接规范；用户同时授权实现时才落地主题、组件和示范页面，不自动安装依赖。
需要追溯参考或选择配套设计技能时，读取 [GitHub 来源与取舍](references/frontend-sources.md)；
这些外部技能不构成运行依赖，也不将其所有偏好叠加为项目规则。

## 工作流

1. 先检查根目录、现有 `AGENTS.md`、README、目录结构、依赖与构建配置、启动入口、测试和现有文档。
   记录可验证的项目事实、已有有效约定和待确认信息；不要从文件名或用户预期推断技术已被采用。
   对已确认 UI，还检查图标导入、高频操作区和现有提示/无障碍模式；组件库不能证明已采用其图标系统。
2. 将工程规范库作为可选增强来源。调用 `tibishu-note-search` 前，先确认技能可用，
   并从进程环境读取 `TIBISHU_NOTES_PATH`；Windows 进程值为空时再查用户环境值，
   确认路径可读。未配置、路径不可访问或技能不可用时，不调用检索技能，不要求先配置才能继续。
   检索失败时也不阻塞初始化：记录原因与未读取的来源，依据仓库事实、用户明确决定和本技能
   内置契约继续；不得声称已读取或应用笔记。用户明确要求必须核对某篇笔记时，将该核对项
   标为未完成并说明缺少的输入，仍推进不依赖它的工作，不宣称整项要求已完成。
   可用时精确检索工程规范库，将工程规范库使用说明、项目初始化、通用架构、质量保障和
   AI 协作交付闭环作为参考；按实际采用或用户明确选定的技术选择语言、UI、运行时、接口
   与部署规范，区分已实现和计划。先看名称和 Blog front matter，需要落地规则时才读正文。
   例如，依赖、源码或构建配置证实 React 时，检索 `React`、`TypeScript` 及实际采用的生态技术；
   不能因为笔记存在而假设 React Router、TanStack Query、Zustand、Redux、Next.js、Wails 或特定 UI 组件库已被采用。
   对已有 UI 或用户明确要求新建前端的项目，额外按需检索前端视觉风格与组件动效、
   前端 UI 交付与视觉验收，以及实际采用或已选定框架对应的
   React 或 Vue 规范、实际采用的组件库或样式系统规范，以及质量规范。只有依赖、
   源码、配置或用户已确认决定支持时才引用它们；组件库、Tailwind、Skill、MCP、
   浏览器或截图目录的存在都不足以证明项目已采用对应方案。仅当仓库存在跨页面高频图标操作区，
   或本轮范围明确涉及图标新增、替换或统一时，检索图标系统与紧凑操作区规则；它用于比较和
   记录决策，不能指定某个默认图标库。
3. 在任何写入前输出简短的“适用规范、项目事实、待确认项、文档计划和交付准备度”。
   交付准备度只记录已经存在的设计来源、范式和验证能力，以及阻止可靠交付的缺口；
   不要把通用建议伪装成项目已有能力。对于已确认 UI，额外列出设计来源、可复用范式、
   关键状态和视觉或设备验收方式；缺失的事实标为待确认，获授权建立的基线单列为本次设计决策。
   对每项观察保留对应的仓库路径、配置、命令输出或用户已确认决定，以便在最终建议中追溯。
   若缺少会影响文档范围的关键事实，保留“待确认”而不编造。
   仅在无法安全继续时请求用户补充。
   对已确认 UI，准备度记录必须明确区分：项目产品与设计事实；已安装或项目声明的
   UI 运行时与 token；可选的 Skill、MCP 或浏览器工具；以及仅在用户提供或项目
   已批准时有效的外部视觉参考。同时记录页面类型及相应任务模式、可复用范式、
   服务端数据/本地状态/URL 状态边界、国际化与可访问性要求、以及真实存在的视觉或
   设备验收能力。对实际支持的国际化，记录翻译机制与入口、消息键归属、日期/数字/货币格式、
   长文本、语言切换及验收；不支持标为“不适用”，机制或行为未知标为“未确认”，不得从依赖、
   目录或工具推断。对适用的图标范围，额外列出图标系统是已采用、待决策还是不适用，并记录
   来源、包体或编译约束、可访问名称与提示方式；未知事实标记缺口，新选择明确标注依据与实现状态。
4. 根据已选规范和仓库事实创建或更新项目文档。保留已有有效约定，说明真实冲突。
   选择维护成本更低、与当前项目更一致的方案。
   交付物的选择条件和内容边界见 [文档契约](references/document-contract.md)。
   UI 文件依据统一判定表选择，具体内容、来源和实现/验证状态遵循前端设计契约；
   不将设计计划或工具存在误写成已实现的系统与验收能力。
5. 通过仓库实际提供的命令验证安装、启动、格式化、测试和构建说明。对已确认存在交互 UI 且具备足够事实的项目，验证文档是否说明设计来源、关键交互状态和视觉或设备验收方式；没有自动化工具时明确记录人工验收边界，而不是承诺尚未建立的截图或端到端门禁。
   未知命令标记为“待补充”，不得捏造。
   对新增或修改的 Markdown 使用可用 lint 工具检查；没有工具时做人工检查并说明限制。
   UI 验证范围须覆盖本次文档中已经证实的状态、语言、主题、响应式、键盘和焦点
   约束；对实际支持的国际化，验收翻译入口、代表格式、长文本和语言切换行为。只能报告实际
   运行的命令和实际具备的浏览器、设备或截图能力。
   对建立的设计基线，检查风格是否已落实为具体 token、组件变体、图标映射、动效参数与
   可执行的人工验收步骤；“简洁美观、统一、有动效”等形容词不能单独作为完成证据。
6. 汇总采用的知识库笔记、创建或更新的项目文件、已确认的交付护栏、待确认事项和推荐的下一步。
   固定附上“初始化后修复建议”，按“缺失”“过时或冲突”“未验证”“需要决策”分类，并为每项
   列出优先级（阻止开发 / 下一项功能前 / 可延后）、目标文件或能力、事实证据、影响和最小下一步。
   仅当已确认的项目事实确实需要某项规则、文档或验证能力时，才报告“缺失”；仅当现有文档或规则
   与仓库事实、真实命令结果或用户已确认决定相矛盾时，才报告“过时或冲突”。不要把可选的最佳实践、
   尚未采用的工具或单纯可优化的文字列为缺失或过时。按影响排序建议，避免以大而全的初始规范阻塞项目。

## 约束

- `AGENTS.md` 必须简洁、直接可执行，并针对当前仓库改写；不得机械复制通用笔记全文。
  要求代理修改前检查事实、同类实现、契约与测试，修改后报告真实验证。替换已有品牌、
  全局组件系统或其它超出本轮授权的高影响选择需先确认；授权内的可逆设计细节可直接决定。
  它不得取代详细设计或测试文档。
- 仅为实际采用或用户已明确决定采用的技术创建规范；空仓库的决定标为“已选定／尚未安装实现”，
  不虚构脚本、入口或依赖。未决定的技术只列待决策，不生成专属规范或空 ADR。
- 不因 Skill、MCP、知识库笔记、目录或其它项目经验存在，就推断框架、组件库、设计
  方向、外部视觉参考、浏览器自动化或截图回归已被当前项目采用。
- 不因项目采用某个 UI 组件库，就推断它的图标库、图标尺寸、状态变体或 Tooltip 策略已经
  被采用；跨页面图标系统的新增或替换仍须由仓库事实或用户明确授权支持。
- 文档必须区分项目专属事实与通用经验。除非用户明确要求且规则已证实具有普适价值，否则不修改 Tibishu 工程规范库。
- 不修改或记录 `.env`、`.evn`、令牌、密钥、个人数据和其他敏感信息。
- 不覆盖用户已有文档；需要改写时保留有价值内容，删除过时或重复内容，并说明影响。
- 不因 AI 协作闭环而默认创建项目级 Skill、组件库、设计系统、截图测试、CI 工作流、模板或新依赖；这些能力必须由仓库事实或用户明确授权支持。
- 修复建议必须区分已证实的问题与待用户决定的方向，并给出证据；建议本身不授权修改项目功能、依赖、CI 或用户拥有的文档。
