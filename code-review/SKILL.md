# 代码审查

围绕用户目标和本次审查范围，找出有证据支持、会造成实际影响且可采取行动的问题。审查深度随风险调整；不要把风格偏好或无关重构混入发现。

## 审查范围

先区分变更审查与模块审计。未特别说明时，按 diff 审查：检查改动及理解其影响所必需的邻近调用方、契约和配置，不把整模块审计当作默认范围。用户明确要求模块审计时，再覆盖该模块的实现、公开边界、关键调用方和相关测试，并在结果中说明检查边界。只有证据支持时才归因于当前改动或历史问题；无法确认时直接报告缺陷，不推断其来源。用户指定文件或范围时遵守该范围。

## 工作方式

1. 确认预期行为与审查类型；读取对应范围的代码、调用方、配置、数据/API 契约及项目约定。
2. 沿高风险路径检查：diff 审查覆盖变更实际涉及的权限与信任边界、输入、失败恢复、并发、资源、兼容性、持久化或部署影响；模块审计检查所定模块内与其风险相关的维度。
3. 用代码路径、现有测试或适用的项目命令核实关键发现。无法验证时说明证据缺口，不把假设写成已证实问题。
4. 先报告影响大且容易触发的问题，合并同一根因，避免重复项。
5. 若当前宿主全局规则要求在主会话的代码审查中联动异构模型做独立复核（例如 Antigravity 调用本机 Codex `read-only` 盲测复核），除非用户明确要求跳过、非代码仓库或处于被委派的 worker 防递归上下文，须完成本方独立判断并调用外部复核，逐条核实双方发现与分歧后合并输出。

按变更涉及的风险读取专项参考：

- [Go](references/go.md)：goroutine 退出、channel 阻塞、资源释放和错误传播。
- [Python](references/python.md)：事件循环阻塞、取消传递、异常处理和资源所有权。
- [TypeScript](references/typescript.md)：外部输入与运行时校验、类型收窄，以及公共类型兼容性。
- [Security](references/security.md)：资源级授权、注入/SSRF/路径遍历边界、凭据泄露和供应链风险。
- [Data & Concurrency](references/data-and-concurrency.md)：数据库兼容迁移与锁风险、Redis 锁租约竞争、部分失败重试和配置预算冲突。

检查回归测试时，确认新增或修改的测试从可观察的用户/调用方入口验证行为（理想情况下先在修复前复现失败），避免只断言内部实现或 mock 掉被测规则。

## 输出

先注明实际审查范围，再按风险从高到低列出可操作发现。每项包含：

- 文件位置；
- 触发条件；
- 实际后果及支持结论的证据；
- 可执行的修复方向。

严重度标签遵循仓库或用户约定；没有约定时，仅在有助于排序时标注高、中、低。说明运行过的检查和结果，以及未覆盖的重要风险。若没有可操作发现，直接说明审查范围和验证缺口。

## 边界

- Diff 审查只把本次变更引入或扩大的实际问题列为发现；模块审计可报告所定范围内的实际问题。仅在证据充分时说明缺陷是否由当前变更引入，无法归因时不作历史判断。仅在判断因果或风险所需时扩展到相邻代码。
- 不报告纯主观偏好、无影响的重构建议、自动格式化问题或未核实的猜测。
- 不把计划执行的测试、工具或检查描述成已运行。
